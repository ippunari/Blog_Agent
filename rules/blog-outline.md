# blog-outline (설계)

> v1.5 2026-11-20 · 운영하며 보강 · 공통 규칙: [common.md](common.md) (특히 2장 도입부, 6장 SEO·AEO·AIO)

## 목적
조사 결과로 제목·훅·목차·키워드 배치·CTA·내부 링크·SNS 포인트를 정한다.

## 입력
- 주제 카드 `briefs/<slug>.md`(`status: 설계 대기`), 조사 노트 `research/<slug>.md`, 대표 한마디(카드 `rep_comment`, 있으면), 키워드, 글 종류
- 카드에 D43 키워드 절(「키워드 (D43 갱신)」 또는 D43 이후 blog-topic이 만든 「상위 구성」)이 없으면 **먼저 키워드를 D43으로 갱신**한다 (blog-topic 키워드 단계 그대로. 주제·점수·순위는 바꾸지 않음)

## 출력
- 설계안 **`outlines/<slug>.md`** (별도 파일, D44) → blog-draft로
- 카드: `status: 초안 대기` (사람 실습 카드이고 결과 전이면 `실습 대기`, D45), `outline: outlines/<slug>.md (날짜)`
- 발행 완료·중단 때 `outlines/`도 research·drafts·factcheck와 같이 `done/YYYY-MM/`·`dropped/`로 옮긴다

## 사람 확인 지점
- 없음 (최종 확인은 blog-publish 미리보기에서). 보고는 짧게(경로·추천 제목·H2·경고) 하고 기다리지 않는다. 설계안 전체는 요청할 때만 (D44)

## 규칙

### 키워드 배치
- 메인 키워드 1 + 질문형 서브 키워드 3~5 (blog-topic 결과)
- 제목 앞쪽 / 메타 설명 / slug / 첫 문단 200자 이내 / H2 절반 이상 / FAQ
- 질문형 서브 키워드는 그대로 H2로 쓴다 (서브 키워드 두 개를 H2 하나에 함께 넣어도 된다)
- **속보의 사건 검색어**(질문형이 아닌 날짜·사건 검색어, 예: 「php 脆弱性 11月19日」)는 그대로 H2로 쓰지 않고 제목·첫 문단 200자 이내·「何が起きた？」 H2에 녹인다 (예: 「11月19日のPHP脆弱性、何が起きた？」). H2 절반 이상 계산에는 사건 검색어도 넣는다 (D44)
- 억지 반복 금지

### 제목
- 전각 28~35자, 메인 키워드 맨 앞
- 본문이 제목의 약속을 지킬 것 (낚시 금지)
- 후보 3개 → 1개 추천 + 이유
- 다른 글(기존 글 목록)과 같은 제목 금지
- 틀은 글 종류를 기본으로 한다. 속보는 「속보」 틀을 후보 하나로 함께 낸다

| 글 종류 | 제목 틀 |
|---|---|
| 속보 | 「〇〇発表｜日本の中小企業への影響は」 |
| 사용법 | 「〇〇の使い方｜できること・料金・商用利用【2026年版】」 |
| 업무 활용 | 「〇〇業務をAIで〇割減らす｜中小企業の手順と実例」 |
| 도입 가이드 | 「中小企業のAI導入、費用はいくら？」 |
| 보안 사고 | 「〇〇不正アクセスとは｜自社も当てはまるか3つの確認点」 |
| 보안 대책 | 「〇〇までにやること【2026年版】」 |
| 개발 | 「〇〇が会社によって2〜3倍違う理由」 |

### 훅
조사 노트에서 하나를 고른다: ① 놀라운 수치 ② 독자가 자기 일로 느낄 사실 ③ 직접 써 본 결과 ④ 대표 한마디(있으면)

### 목차와 분량
| 글 종류 | 분량 | 목차 |
|---|---|---|
| 속보 | 1,500~2,500자 | 3行まとめ / 何が起きた？ / 日本の中小企業への影響は？ / 今やること / (代表ヤンのひとこと — 있을 때만) / FAQ 2 / SOURCES |
| 사용법 | 4,000~6,000자 | 結論 / できること・料金 / 始め方(画面) / 使ってみた / 業務での使い方 / 注意点 / (代表ヤンのひとこと — 있을 때만) / FAQ 3~5 / SOURCES |
| 업무 활용 | 4,000~6,000자 | こんな悩み / AIで変わること(数値) / 手順 / 実例 / 失敗しないコツ / FAQ / SOURCES |
| 도입 가이드 | 5,000~8,000자 | 직답 / 費用・期間 / 進め方 / よくある失敗 / 自社に合うか判定 / FAQ / SOURCES |
| 보안 사고 | 4,000~8,000자 | 3行まとめ / 何が起きた(公式発表ベース) / 原因 / 自社も当てはまる？ / 今日確認すること / FAQ / SOURCES |
| 보안 대책 | 4,000~6,000자 | 3行まとめ / 期限とリスク / 手順 / 判定表 / FAQ / SOURCES |
| 개발 | 4,000~6,000자 | 직답 / 理由 / 事例・データから / 発注前チェックリスト / FAQ / SOURCES |

### 검색 의도와 겹침 (D45)
- 노트 「상위 10개 글 유형」(속보는 카드 「상위 구성」)을 보고 글 형식(가이드/목록/비교/뉴스·해설)을 정한다 (common.md 6장 SEO 1)
- 메인 키워드가 제목에 들어간 우리 기존 글이 있으면 어떻게 구분하는지 적는다. 구분이 안 되면 새 글 대신 개편을 사람에게 묻는다 (1키워드 1글)
- 노트 「차별 포인트」마다 놓을 섹션을 정한다. 일반 글은 경쟁 글이 공통으로 다루는 핵심이 목차에 있는지 확인한다

### 개편 글 (D45)
- URL·slug는 바꾸지 않는다. 제목은 기본 유지 — 바꾸면 이유를 적는다 (이미 순위가 있을 수 있다)
- 섹션마다 바뀜/유지/추가/삭제와 근거(노트 「기존 글에서 낡은 사실」)를 표로. 의미 있는 수정이면 업데이트일을 바꾼다 (common.md 6장 11)
- 같은 키워드를 다투는 우리 글이 있으면 역할을 나누고 서로 링크한다

### 실습 대기 (D45)
- `trial: 사람`이고 노트에 결과가 아직 없으면 「使ってみた」 섹션을 「◆ 실습 대기」로 비워 두고 카드를 「실습 대기」로 한다
- 결과가 노트에 들어오면(blog-research) 그 섹션만 채우고 「초안 대기」로

### 마감이 지난 속보
- 설계를 시작할 때 속보 마감이 이미 지났으면 속보로 설계하지 않고 깊이 있는 글로 돌릴지 사람에게 알린다 (D34)

### 경로와 글 종류가 겹칠 때 (D44)
- 속보 경로인데 글 종류가 보안 대책 가이드·보안 사고 해설 등일 때: **뼈대·분량은 속보 목차**를 따르고, **도입부·제목 틀·CTA 종류·「今やること」의 내용**(짧은 판정표·체크리스트)은 글 종류를 따른다. CTA 위치는 속보 규칙(글 끝만)
- 이유: 속보는 72시간 마감 — 깊이 있는 글 분량으로 늘리면 마감을 넘긴다

### 소제목
- 번호·영어 라벨(디자인, 작게. 예: 01 At a glance) + 질문형 일본어 소제목(실제 H2) 둘 다
- H2 4~8개, 각 H2 바로 뒤 첫 문장에 40~80자 직답
- 주요 섹션 끝에 「まとめ」 (ひかりちゃん)
- 섹션마다 형식(문단/번호 목록/표/상자)을 정한다. 순서는 번호 목록, 비교는 표 (AEO, HowTo 대신 번호 목록)
- 「〇〇とは」 키워드는 그 H2 직답을 「〇〇とは、〜です。」 정의 문장으로

### CTA 위치
- 본문 중간 1회(판정표·체크리스트 직후) + 글 끝 1회
- 속보는 글 끝만
- 어떤 CTA인지는 common.md 1장. 버튼 문구·링크는 common.md 1장 「CTA 버튼」 표 그대로 (D45)

### 내부 링크
- 같은 주제 축 글 2~3개 + 기둥 글 1개, 위치를 표시

### 역링크 (D45)
- 발행 후 새 글로 링크를 걸 기존 관련 글 2개 이상과 넣을 곳·앵커 텍스트를 정한다 (common.md 6장 SEO 7). 넣는 일은 blog-publish
- 넣을 곳은 그 글을 실제로 읽고 H2 이름으로 적는다 (짐작 금지) — 점검 스크립트 `--verify-links`가 그 글에 같은 소제목 줄이 있는지 확인한다. 발행 직전에 blog-publish가 다시 확인한다

### 태그
- 기본 태그 = 주제 축(AI·보안·개발), 보조 태그 = 글 종류 (common.md 6장 SEO 12)

### 갱신 조건
- 속보는 노트 「아직 확인하지 못한 사항」 중 나오면 글을 고칠 것과 섹션을 적는다 (common.md 6장 SEO 11)

### SNS 포인트
- 수치 1, 의견 1, 질문 1을 표시 (blog-distribute·blog-newsletter가 사용)
- 의견은 **편집부 의견**(조사 노트의 사실에 근거, S번호 표시). 대표 한마디가 없으면 대표 의견으로 쓰지 않는다

### FAQ
- 실제 검색 질문만: 근거 검색어가 카드 키워드 절에 기록된 것이고, 질문 문장에 그 단어가 다 들어간다
- 노트로 답할 수 없는 질문은 만들지 않는다

### 설계안이 지키는 선
- 쓸 사실은 조사 노트의 S번호로만 정한다
- **H2·FAQ가 묻는 질문의 답은 노트에 있어야 한다.** 없으면 blog-research 방식으로 노트에 S행을 보충하고(기존 행은 고치지 않음, 속보는 15분 이내), 못 찾으면 H2를 바꾼다. 질문만 하고 답을 링크로 넘기지 않는다
- 직답·판정표의 범위는 S번호 원문보다 넓히지 않는다 (예: 노트가 8.1만 말하면 「8.1系以前」 금지)
- 내부 링크는 링크할 글의 내용을 확인한다. 다른 사건용 글을 일반 글처럼 소개하지 않는다
- 노트 「아직 확인하지 못한 사항」은 「쓰지 않을 것」에 옮겨 적는다
- 일본어로 쓰는 것은 제목·메타·H2·직답 메모·FAQ 질문·앵커 텍스트·SNS 포인트뿐. 나머지 설명은 한국어
