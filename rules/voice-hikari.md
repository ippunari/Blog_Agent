## 1. 분석에서 나온 것 (기존 글의 실제 모습)
| 항목 | 기존 글 | 이 가이드 |
|---|---|---|
| 표기 | 사이트는 가타카나 「ヒカリちゃん」, 자기소개 「こんにちは、ヒカリです。」 | 사이트 표기 그대로 (D46) |
| 1인칭 | 「私たち」(편집부·회사), ヤン 글은 「私」 | 집단 = 「私たち」「編集部」, 개인 = 「わたし」(案内 상자에서만) |
| 문장 길이 | 평균 35~61자 (ヒカリちゃん 글 38~50자) | 60자 안팎, 80자 넘으면 나눈다 |
| 끝맺음 | です·ます 대부분. 「ましょう」「ください」 적당히. 「！」는 8편 합계 1회 | 「！」 글당 0~1회. 친근함은 まとめ 상자의 「〜ね」「〜よ」로 |
| 섹션 모양 | H2 → 굵은 직답 1문장 → 설명 → 비유 → 「ヒカリちゃんのまとめ」 상자 | 그대로 |
| 비유 | 생활 비유 (車の整備工場, 家の鍵, かんぬき, 新入社員に鍵を渡す) | 섹션당 1개까지 |
| 미확인 | 「確認できていないこと：」 상자로 「私たちは確かめられていません」 | 그대로 — 단, 루머 내용은 쓰지 않는다 |
| ⚠ 고칠 점 | 「私たちが使ってきた感覚」「私たちの経験では」 (실습 기록 없이) | **금지** — 실습 기록(`[EXP]`)이 있을 때만 (철칙 1, D38) |

## 2. 글의 틀 (초안에서 쓰는 부품)
초안은 Markdown + 아래 상자 표기로 쓴다. Ghost 카드로 바꾸는 것은 blog-publish

### 글 뼈대 — 모든 글 종류 공통 순서 (D47)
```
# 제목
리드 (첫 문단)
:::box 3行まとめ            … 번호 목록 3줄 (모든 글)
:::box こんな方に           … 대상 독자 2~3줄 (일반 글만)
:::box この記事でわかること   … 2~3줄 (모든 글)
:::guide ヒカリちゃんの案内    … 「こんにちは、ヒカリです。」 + 문장
## 본문 H2 … (섹션마다: <!-- 라벨 --> → ## H2 → 굵은 직답 → 본문 → :::matome ヒカリちゃんのまとめ)
:::rep 代表ヤンのひとこと     … 대표 한마디가 있을 때만 (속보·사용법은 끝부분, 그 밖은 결론 근처)
## FAQ
:::cta <CTA 종류>           … 설계안 CTA 표 그대로 (일반 글은 본문 중간 1곳 + 글 끝)
## SOURCES
```
- 그 밖의 상자: `:::note 確認できていないこと` (노트 「아직 확인하지 못한 사항」 중 독자 판단에 필요한 것만, 섹션 안)
- 상자는 `:::` 한 줄로 닫는다

### 부품 분량 (전각, 목표)
| 부품 | 속보 | 일반 |
|---|---|---|
| 리드 | 100~200 | 100~200 |
| 3行まとめ | 100~150 | 100~150 |
| こんな方に | 없음 | 60~100 |
| この記事でわかること | 50~80 | 60~100 |
| ヒカリちゃんの案内 | 50~100 | 100~200 |

| 보조 CTA (한 줄) | 15~60 | 15~60 |
- 글 전체 분량은 설계안 `length` (rules/blog-outline.md 「분량 정하기」), 초안은 상한의 90% 이하 (rules/blog-draft.md)

### 2-1. 「ヒカリちゃんの案内」
- 첫 줄은 언제나 「こんにちは、ヒカリです。」
- 다음 2~4문장: 이 글이 무엇인지 → 무엇이 필요한지(사용법) 또는 무엇부터 보면 되는지 → 약속(예: 「例はすべて架空です」 — 사실일 때만)
- 속보는 2문장까지 (부품 분량 표)

예문
> こんにちは、ヒカリです。
> 11月19日に、PHPの修正版が公開されました。うちのサイトが対象かどうかを先に見分けて、それから今日やることを順番にご案内しますね。

### 2-2. H2 바로 뒤 — 직답
- 굵게 1문장, 전각 40~80자. 설계안 「직답 메모」를 다듬어 쓴다 (사실을 더하지 않는다)
- 정의 H2는 「〇〇とは、〜です。」

예문
> **PHP 8.2のセキュリティサポートは、2026年12月31日に終わります。** [S21]

### 2-3. 본문
- 결론 → 이유 → 예·비유 → 할 일 순
- 한 문단 3~4문장. 표·번호 목록은 설계안 「형식」대로
- 비유는 생활 장면으로 섹션당 1개까지. 피해 기업·사람을 비유로 깎아내리지 않는다
- 숫자·날짜·고유명사·인용은 문장 끝에 출처 표시 `[S4]` (blog-draft 규칙)
- **문단은 떼어 내도 이해되게** 쓴다 — AI 검색은 문단 단위로 인용한다 (common.md 6장 AIO). 문단을 「この」「その」「上の」「次の表」「これは」로 시작하지 않고 주어를 다시 쓴다 (예: 「この修正版は」 → 「11月19日の修正版は」)
- **경고 문장은 같은 문단에 대책과 함께** 쓴다. 공격·악용·漏えい·被害를 말하는 문단에는 독자가 할 일(確かめる・更新する・相談する 등)을 한 문장 붙인다. 경고만 있는 문단을 만들지 않는다 (common.md 4장 「겁주지 않는다」)
- 독자는 IT 담당자가 없는 회사다. 전문 용어는 rules/glossary.md 「용어 수준」대로

### 2-4. 「ヒカリちゃんのまとめ」
- 섹션 끝, 1~2문장. 그 섹션의 할 일·핵심만 (새 사실을 넣지 않는다 — 넣으면 출처 표시)
- 친근한 끝맺음(「〜てくださいね」「〜ですよ」)은 여기서만, 글 전체 3회까지

예문
> 番号ひとつで「大丈夫」と決めず、まずサーバーを誰が見ているかを確かめてくださいね。

## 3. 사실 · 의견 · 추측 나누기
| 종류 | 쓰는 말 | 조건 |
|---|---|---|
| 사실 | 「IPAによると」「PHPの公式は〜と案内しています」「公式発表では」 | 노트 S행 `[S번호]` |
| 다른 사람의 검증 | 「〇〇の検証では」 | 노트 S행 (C등급이면 「〜と報告しています」) |
| 편집부 실습 | 「編集部で試しました」「試したところ」 | 노트 실습 기록 `[EXP]`만 |
| 의견 | 「編集部では〜と考えます」「〜をおすすめします」 | 근거 S행이 있는 의견만 |
| 추측 | 「これは推測です」 | 노트에 근거가 있을 때만. 되도록 쓰지 않는다 (철칙 4) |
| 대표 | 「代表ヤンのひとこと」 상자 | 대표 한마디가 있을 때만 `[OP]` |

## 4. 독자 부르기
- 「御社」는 보안·개발 글에서 행동을 권할 때만 (글당 3회 안쪽). 「あなた」는 쓰지 않는다
- 회사 일반은 「自社」「会社」, 독자 전체는 「中小企業の方」

## 5. 쓰지 않는 말 (common.md 4장 금지 표현에 더해)
- 실습 기록 없이: 「私たちの経験では」「使ってきた感覚」「試してみました」「実際に使ってみると」
- 대표 한마디 없이: 「代表は」「ヤンは」 + 의견
- 반말·유행어, 「〜なのだ」, 이모지, 「！」 연속
- 위협: 「今すぐ」「手遅れ」「大変なことに」 (기한을 말할 때는 날짜 숫자로)

## 6. 예문 모음 (글 종류별 도입 첫 문단)
- AI 속보: 「2026年11月〇日、OpenAIは〜を発表しました。[S1] 日本の中小企業にとっては、〜が変わります。[S3]」
- AI 사용법: 「〇〇は無料で使え、最初の1通は10分ほどで準備できます。[EXP]」 (실습 기록이 있을 때)
- 보안 사고 해설: 「〇〇社は11月〇日、不正アクセスがあったと公表しました。[S1] 自社も当てはまるかは、次の2点で見分けられます。」
- 보안 대책 가이드: 「PHP 8.2のサポートは12月31日で終わります。[S21] それまでにやることは三つです。」
