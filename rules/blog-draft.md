# blog-draft (초안 작성)

> v1.8 2026-11-28 · 운영하며 보강 · 공통 규칙: [common.md](common.md) (특히 3장 필자, 4장 문체) · 목소리: [voice-hikari.md](voice-hikari.md) · 용어: [glossary.md](glossary.md)

## 목적
설계안대로 섹션별 초안을 쓰고, 모든 사실 문장에 출처를 연결해 둔다.

## 입력
- 설계안 `outlines/<slug>.md` + 조사 노트 `research/<slug>.md` + 주제 카드(대표 한마디가 있으면) + 공통 규칙 + 목소리 가이드 + 용어집

## 출력
- `drafts/<slug>.md` → blog-factcheck로
- 파일 머리말: 글 종류 / 필자 / 메인·서브 키워드 / 주·보조 CTA / 분량 범위 / 설계안·노트 경로
- 본문(일본어) → `## SOURCES`(쓴 S번호 목록) → `## 초안 메모`(한국어, 발행하지 않음: `[?]` 목록, 조사 보충 필요, 용어집 추가 후보, 설계와 달라진 점)
- 카드 `status: 대조 대기`
- 사람 실습 결과 전(`trial: 사람` + 노트 「◆」)이면 「使ってみた」 섹션은 자리 표시 `:::trial 実習待ち` 상자 하나 (아래 「사람 실습 자리 표시」, D79)

## 사람 확인 지점
- 없음 (짧게 보고하고 기다리지 않는다. 최종 확인은 blog-publish 미리보기)

## 규칙
- **번역하지 않고 설명한다** (D103): 섹션마다 노트를 읽고 내용을 이해한 뒤, **IT 담당자가 없는 사장에게 말로 설명하듯** 일본어로 먼저 쓴다 — 영어 원문 문장을 옆에 두고 한 문장씩 옮기지 않는다. 그다음 사실 문장에 [S번호]를 붙이고, 근거가 없는 사실은 빼거나 「조사 보충 필요」. 사실을 한 문장에 하나씩 이어 붙이면 문장마다 맞아도 이어 읽으면 번역문이 된다 (2026-11-28 Claude 글: 사용자 「왜 이런 이상한 일본어를 작성하는 거니?」)
- **처음 읽는 사람이 알 수 있게** (D103):
  - **정의 먼저**: 메인 키워드가 독자가 처음 듣는 말이면(서브 키워드에 「〜とは」), 리드 첫 문장은 「それが何か」 — 그다음 무슨 일이 생겼는지. 첫 H2도 정의 섹션 (설계안 목차대로)
  - **리드·案内·첫 H2는 역할이 다르다**: 리드 = 정의 + 훅 + 직답 / 案内 = 이 글을 **어떤 순서로 읽으면 되는지·약속**만 (리드 사실을 다시 말하지 않는다) / 첫 H2 = 리드보다 **자세한 내용**(날짜·누가·어디서)으로 시작. 같은 사실을 세 번 말하지 않는다
  - **머리 문장(제목·메타·리드·3行まとめ)은 핵심만**: 제공 조건(ベータ·順次提供·対象プラン 등)은 본문의 해당 섹션에서 쓴다 — 사실은 본문에 남는다
  - **화면·메뉴는 어디의 무엇인지**: 「メニュー」「設定」「画面」「項目」을 처음 쓸 때는 어느 앱의 어디를 누르면 나오는지, 또는 항목 이름(「アプリとしてインストール」)까지. 「メニューが出ないとき」처럼 무슨 메뉴인지 모르는 말을 머리 문장에 쓰지 않는다
  - **출처는 발행처 + 문서 종류**: 「Anthropicのヘルプセンター」「Googleのブログ」「OpenAIの発表」. 「公式ヘルプ」「公式の日本語ヘルプ」는 쓰지 않는다
  - **영어 화면 이름은 쓰지 않는다**: 노트에 일본어 화면 이름(공식 일본어 표기)이 있으면 그것만 — 일본 독자는 일본어 화면을 본다 (「Install as app」 ✕). 폴더·제품 같은 고유 이름(「Claude Apps」)은 그대로
- 섹션 단위로 설계안 목차 순서대로 쓴다. **H2 문구는 설계안 그대로** (키워드 배치가 걸려 있다)
- **조사 노트에 없는 사실은 쓰지 않는다.** 설계안 「쓰지 않을 것」도 쓰지 않는다. 필요한 사실이 노트에 없으면 그 문장을 빼고 「초안 메모」에 「조사 보충 필요」로 적는다. 빼면 섹션이 성립하지 않으면 멈추고 blog-research로 되돌린다
- 범위를 넓히지 않는다: 원문이 「8.1」이면 「8.1系以前」으로 쓰지 않는다 (D44 ⑨). 의견은 「編集部では」로 표시한다
- 필자 목소리(voice-hikari.md)와 글 종류별 도입부(common.md 2장)를 지킨다
- **분량**: 설계안 `length` 범위 안. 상한의 90%를 넘으면 경고(여유가 적다), 상한을 넘으면 오류 (D47, D58). **분량이 빠듯하면 설명을 깎지 않고 덜 중요한 사실을 뺀다** — 독자가 이해하는 것 > 사실 개수 > 글자 수
- **사실은 두 박자로** (D58): 「무엇이 있다(사실)」 + 「그래서 독자의 사이트·회사에 무슨 뜻인가」. 기술 사실(任意コード実行·署名検証の回避 등)은 흐린 말로 바꾸지 말고, 용어집에 있으면 그 용어 + 괄호 풀이, 없으면 「〜できてしまう弱点で、〜のおそれがあります」처럼 결과까지. 결과 설명의 근거는 노트 또는 사이트 용어집 설명(`glossary_site.json`의 desc)
- **한 문단 한 화제** (D58): 관계없는 사실(예: 취약점 내용과 8.6.0 공개)을 한 문단에 넣지 않는다
  - 세는 법: 제목·공백·출처 표시·Markdown 기호·링크 URL·주석·SOURCES·초안 메모 제외 / 표·상자·CTA 문구·링크 앵커 포함
  - 하한보다 짧으면 늘려 쓰지 않는다 → 「조사 보충 필요」 (사실이 모자란 것)
- **글 뼈대**는 rules/voice-hikari.md 2장 순서 그대로. 「3行まとめ」는 상자
- **차별 포인트 필수** (D47): 설계안 「차별 포인트 배치」에서 섹션을 정한 항목은 **모두** 그 섹션에 쓰고, 쓴 블록(문단·표·목록·인용) 바로 위 줄에 `<!-- 차별 N -->`(N = 설계안 번호)을 단다. 그 블록에 항목의 근거 S번호가 있어야 하고, 판정표·표·체크리스트 항목이면 블록이 표여야 한다. 쓰지 못한 항목은 초안 메모 「설계와 달라진 점」에 「차별 N — 이유」. 표시는 발행 때 지운다. 하나도 없으면 통과하지 않는다 — 새 가치가 없는 글을 대량으로 내지 않기 위해 (Google 스팸 정책 「scaled content abuse」)
- 문단 독립성·경고 문장 모양·용어 수준은 voice-hikari.md 2-3, glossary.md 2-1
- 첫 문단(제목 바로 아래 리드) 200자 이내에 메인 키워드와 제목 질문의 직답 (속보는 사건 검색어도)
- **리드 첫 1~2문장에 설계안 「훅」을 둔다** — 사실 나열로 끝내지 않는다. 훅의 근거 S번호가 리드 앞 2문장에 있어야 한다 (D53). 정의 문장이 첫 문장이면 훅은 둘째 문장 (D103)
- **훅에 쓰는 원문 주장은 조건을 그대로** — 「특정 등급·버전·설정에만」 붙은 말을 「전체」로 넓히지 않는다 (예: 「Critical 등급은 기본이 아닌 설정이 조건」 → ✕ 「PHPの脆弱性は既定の設定なら影響を受けない」). 훅은 놀라게 하려고 주어를 넓히기 쉽다 — 시험 두 번 모두 같은 실수 (D54)
- **리드는 한 줄기로 읽히게** — 문장마다 앞 문장을 받아서 잇는다(ところが・そのため・〜のままでも 등). 훅 뒤에 날짜·사실을 따로 끼우지 않는다: 사실은 맨 앞 1문장, 마지막 직답은 훅을 받아서 (D53)
- **리드와 3行まとめ는 같은 말을 되풀이하지 않는다** — 리드 = 훅 + 직답, 3行まとめ = 리드에 없는 판단 기준·할 일 (D53)
- **서브 키워드는 H2에만 두지 않는다** — 핵심어(메인 키워드 낱말을 뺀 말: バージョン·確認·アップデート·対応 등)를 H2 밖 본문에도 쓰고, 리드 200자·메타 설명에 하나 이상 (D53). 검색어인 말은 쉬운 말로 바꾸지 않는다 (glossary.md, voice-hikari.md 7-2)
- H2 바로 뒤 첫 문장은 굵게 쓴 직답, 전각 40~80자 (설계안 직답 메모를 다듬되 사실을 더하지 않는다)
- 내부 링크·CTA 버튼 문구·링크는 설계안 표 그대로
- **그림 표시** (D97): 설계안 「그림 자리」 표의 N번째 행마다, 그 섹션 안에서 **그림이 뒷받침하는 블록 바로 위 줄**에 `<!-- 그림 N -->`을 둔다 (`<!-- 차별 N -->`과 같은 방식). 편집부 그림이면 그 블록에 그림의 사실 S번호가 있어야 한다. 못 두면 초안 메모 「설계와 달라진 점」에 「그림 N — 이유」. blog-publish가 이 자리에 그림을 넣는다 (D96 이전 설계안은 해당 없음)
- **검색 화면** (D95): 설계안 「검색 화면」은 읽되, **AI 개요 문장은 본문의 사실이 아니다** — 사실은 노트 S행에서만 (철칙 3·4). 형식은 설계안 목차 「형식」 칸이 이미 AI 개요 답 형식을 반영했다. 차별 메모의 「AI 개요에 없음」 항목은 줄이지 않고 쓴다
- **문단마다 주장 한 문장** (D97): 각 문단이 무엇을 말하는지 한 문장으로 말할 수 있어야 한다. 못 하면 주제를 훑기만 한 문단이니 고치거나 지운다 (스스로 대조)
- **구조 되풀이** (D97, 경고만): 문장 시작이 같은 말로 되풀이되지 않게(많이 쓴 시작 3개가 25%를 넘지 않게), 섹션 첫 문단을 「まず・次に・また・さらに・そして」로 잇지 않게, 목록 항목·문단 길이를 기계처럼 고르게 맞추지 않게, 「重要なのは」「ポイントは」「ここでは」처럼 글 자체를 말하는 문장으로 시작하지 않게. 굵은 직답·상자·표·CTA·FAQ는 사이트 형식이라 보지 않는다
- 용어는 용어집 규칙대로 (사이트 용어집 표기, 처음 나올 때 괄호 풀이)

### 문장 표시 (내부용)
| 표시 | 뜻 |
|---|---|
| `[S3]` | 사실 문장, 조사 노트 S3에 근거 |
| `[OP]` | 대표 한마디 인용 (있을 때만) |
| `[EXP]` | 직접 써 본 결과 (조사 노트의 실습 기록) |
| `[?]` | 출처 없는 사실 문장 (blog-factcheck에서 반드시 처리) |

- 문장 끝 「。」 바로 뒤에 붙인다: 「…公開されました。[S4]」. 여러 개면 `[S4][S5]`
- **사실 문장** = **숫자·날짜·이름(제품·기능·메뉴·기관)·범위·조건·누가 말했나**가 든 문장. 표의 칸·번호 목록 줄도 사실이면 표시한다. 대조(blog-factcheck)는 이 문장만 한다 (D103)
- **설명·이음·독자에게 하는 말은 표시하지 않고 자유롭게 쓴다** — 노트 사실을 풀어 말하기, 「그래서 무슨 뜻인지」, 할 일 권하기. 단 새 사실(노트에 없는 숫자·조건·주장)은 넣지 않는다 (철칙 4). 권하는 말이 출처의 권고를 넓히지 않게 (예: 「フルアクセスを許す前に」를 「使う前に」로)
- 발행할 때 `[S번호]`는 각주 `[1][2]`로 바꾸고 나머지 표시는 지운다 (blog-publish)

### 사람 실습 자리 표시 (D79)
- 설계안 「◆ 실습 대기」 행의 H2는 그대로 쓰고, 그 아래는 **직답 없이** `:::trial 実習待ち` 상자 하나만: 해 볼 작업 3~5줄(한국어, 노트 체크리스트 요약) + 실습 문서 링크. 발행용 문장이 아니다 — blog-publish가 미리보기에서 눈에 띄는 「◆ 실습 필요」 상자로 바꾸고 Ghost 제목에 `[실습 필요]`를 붙인다
- 상자 밖에는 실습 결과를 짐작한 말(「使ってみた」「試しました」 등)을 쓰지 않는다 (철칙 1). 상자는 분량에 세지 않고, 사실 대조·다듬기 대상도 아니다
- 결과가 들어오면(「실습 끝났어」) 그 섹션만 설계안 행대로 다시 쓴다: 굵은 직답 + `[EXP]` 본문(실습한 사람은 「編集部のスタッフ」, 실패도 그대로) + まとめ. 상자가 남은 채로는 점검을 통과하지 못한다

### 짧은 인용 (common.md 5장)
- 글당 2개까지, 각 1~2문장. `>` 인용 줄 + 출처 이름 + `[S번호]`
- 일본어 원문 문장과 25자 이상 같은 부분이 인용 줄 밖에 있으면 전재로 본다 — 새로 쓴다

### 대표 한마디
- 있으면 「代表ヤンのひとこと」 상자로. 뜻을 그대로 살려 일본어로 옮긴다. 한국어 원문은 노트에 보존
- 없으면 대표의 의견·경험을 쓰지 않는다. ヒカリちゃん의 「써 봤어요」는 실습 기록이 있을 때만 (철칙 1)
