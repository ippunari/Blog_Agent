# blog-distribute (SNS 배포)

> v1.6 2026-11-21 · 운영하며 보강 · 공통 규칙: [common.md](common.md)

## 목적
발행한 글을 5개 플랫폼에 맞게 다시 써서 블로그로 사람을 데려온다.

## 언제 (D66)
- **발행 직후 바로**: blog-publish 「발행했어」 점검(after_publish.py)이 통과하면 이어서 만든다. 예약 글은 공개가 확인된 직후(`--verify-live`). 시간을 두지 않는다
- 예약 게시는 쓰지 않는다 — 사람이 확인하고 「올려」 하면 그때 올린다 (SNS 앱 안에 초안을 올려 두는 방법은 없다, D74)

## 입력
- 발행 완료 카드(`briefs/done/YYYY-MM/`)의 최종 글(`drafts/done/`), 설계안의 SNS 포인트(수치·의견·질문), 대표 이미지
- **SNS 문안의 사실은 최종 글에 있는 것만** (철칙 4)

## 출력
- `publish/done/YYYY-MM/<slug>/sns.md` — 플랫폼별 게시글 5개 (UTM 링크 포함, **원본**), 게시 기록 `sns_posted.json`, 카드 `sns:`·`sns_posted_at`·`sns_platforms`
- `sns/YYYY-MM-DD.md` — **날짜별 모음** (그날 발행한 글의 문안을 발행 순으로, 플랫폼마다 ✅ 올림 / ⏳ 「올려」 대기 / ✋ 붙여 넣기 / ❌ 실패). 보기용이라 스크립트가 점검·게시 때마다 다시 만든다
- 공유 드라이브 `03_Blog/sns`의 **날짜별 시트** 「BlogAgent SNS 문안 YYYY-MM-DD」 — 한 행 = 글 1편 × 플랫폼 1곳, 칸 이름에 필터(플랫폼별로 볼 때). 사람은 이것으로 확인한다. 보기용(원본은 sns.md) — 시트를 고쳐도 반영되지 않는다, 고칠 것은 「메모」 칸이나 대화로 (D74)

## 하루 순서 (회차 = 발행 12시 전 아침 / 후 저녁, D76)
1. 글이 공개되면 에이전트가 문안을 만들고 점검 → 그 회차의 글이 모두 통과하면 **회차 시트 1장** 「BlogAgent SNS 문안 YYYY-MM-DD 아침」 (3편 × 5곳 = 15행)
2. 사람이 시트를 읽는다 → 고칠 것은 「메모」 칸이나 대화로 「고쳐」
3. 「올려 아침」 → Threads·Facebook·LinkedIn 자동 게시 (3편이면 9건)
4. 사람이 시트의 ✋ 행(X 3·note 3)을 붙여 넣고, 대표 이미지(시트 주소)를 첨부하고, 올린 주소를 「게시 주소」 칸에 적는다
5. 「다 올렸어 아침」 → 에이전트가 시트를 읽어 기록하고 빠진 것을 알려 준다
- 같은 계정에서 몇 편이 한꺼번에 나가는 것은 일단 허용 — 간격 두기는 13번 전체 연결(정해진 시각 실행)에서

## 사람 확인 지점
- ◆ 날짜별 시트(또는 대화에 보여 준 문안)를 확인한 뒤 「올려」 → 에이전트가 Windsor로 게시. **「올려」가 승인이다** (철칙 2 — 「올려」 없이는 보내지 않는다)
  - 「올려」만: 방금 보여 준 글 / 「올려 <slug>」: 그 글 (slug 자리에 파일 이름·글 주소도 됨) / 「올려 오늘」·「올려 YYYY-MM-DD」: 그날 아직 안 올린 글 전부 — 먼저 「N편 × 플랫폼」 목록을 보여 주고 사람이 한 번 더 「응」 한 뒤 보낸다
- 사람이 직접: X·note 붙여 넣기, Facebook 개인 계정 공유, LinkedIn 개인 계정 — 올린 뒤 「X 올렸어 <slug> <주소>」처럼 알려 주면 기록한다

## 규칙

### 공통
- 플랫폼마다 새로 쓴다 (복사 금지)
- SNS 포인트(수치·의견·질문)를 쓴다
- UTM: `?utm_source={x|threads|note|linkedin|facebook}&utm_medium=social&utm_campaign={slug}`
- 게시 시간: 블로그가 공개된 직후 (일반 글은 오전 8시 공개 직후, 속보는 발행 직후, D66)
- 처음부터 5곳 모두 운영

### 계정
- 기본: 회사 계정
- LinkedIn: 회사 페이지(Windsor) + 편집부 담당자 개인 계정(사람이) (대표 개인 계정은 선택 — 나중에 추가)
- Facebook: 회사 페이지 + 편집부 담당자 개인 계정에서 공유 (대표 개인 계정은 선택)
- 개인 계정 게시도 사람이 확인하고 올린다 (철칙 2). 파일에 개인 이름·계정 ID를 적지 않는다

### 플랫폼별 (형식)
| 플랫폼 | 길이 | 링크 | 해시태그 | 이모지 | 이미지 |
|---|---|---|---|---|---|
| X | 전각 140자 이내 | **답글에** (본문에 넣지 않는다) | 1~2 (끝에) | 0~1 | 대표 이미지 첨부 (사람, 시트 주소에서) |
| Threads | 500자 이내 (권장 150~350) | 본문 끝에 1개 | 0~1 (Threads는 주제 태그 1개) | 0~2 | 링크 미리보기가 OGP(대표 이미지)를 쓴다 — 첫 게시 때 확인 |
| Facebook | 200~400자 | 「リンク」 칸 → 링크 미리보기 (본문에 URL 없음) | 0~2 | 0~1 | 링크 미리보기가 OGP(대표 이미지)를 쓴다 |
| LinkedIn | 300~600자 | 「リンク」 칸 → 본문 끝에 붙여 게시 (D76) | 2~3 (끝에) | 0 | 대표 이미지 글 (Windsor가 올림) |
| note | 1,000~2,000자 | 「全文はブログで」 + 링크 | 3~5 | 0 | 見出し画像 = 대표 이미지 (사람, 시트 주소에서) |

- 대표 이미지 JPEG 공개 주소: blog-publish `ghost_upload.py`가 대표 이미지와 함께 JPEG 사본을 Ghost에 올려 `ghost_post.json` `hero_jpg_url`에 남긴다 (Threads·LinkedIn·X가 webp를 받지 않을 수 있어서, D76)

### 플랫폼별 스타일 (D75)
> SNS는 실제 고객이 들어오는 창구다. 플랫폼마다 **읽는 사람·앞에 세울 것(切り口)·틀**이 다르다. 같은 글이라도 5개가 서로 다른 글로 읽혀야 한다

공통
- **1편 1메시지**: 글의 SNS 포인트(수치·의견·질문) 중 그 플랫폼에 맞는 것 하나를 중심에 둔다. 여러 개를 다 넣지 않는다
- **切り口를 먼저 정한다**: sns.md 플랫폼마다 `### 切り口`에 한 단어로 적는다 (아래 허용 값). 다섯 플랫폼의 첫 문장은 서로 달라야 한다 (첫 20자가 같으면 오류)
- **첫 줄이 전부다**: 접기(「もっと見る」·「さらに表示」) 전에 보이는 첫 줄에 切り口를 둔다. 인사·날짜·「〜が公開されました」로 시작하지 않는다 (Threads의 「ヒカリです。」 한 줄은 예외 — 그다음 줄이 첫 줄 역할)
- **독자가 얻는 것**을 쓴다: 소식이 아니라 「그래서 우리 회사는 무엇을 하면 되나」. 할 일이 있는 글은 할 일 1개를 꼭 넣는다
- **사실은 최종 글에 있는 것만** (철칙 4) — 그중에서도 **3行まとめ·섹션 굵은 직답·설계안 SNS 포인트**(두 번 대조된 문장)에서 가져온다. 표현은 바꿔도 새 사실은 더하지 않는다. SNS용 별도 사실 대조는 두지 않는다 (D76). 수치는 글과 같은 꼴(단위 포함)
- **검색 (D76)**: X·Threads·LinkedIn 첫 두 줄에 블로그 키워드(메인·서브·속보 사건어) 하나를 자연스럽게 — 사람들이 SNS 안에서 그 말로 찾는다. 해시태그도 그 키워드에서. SNS 링크는 대부분 nofollow라 순위를 직접 올리지는 않는다 — 효과는 발행 직후 방문·크롤링·회사 이름 검색
- **끝은 다음 행동 하나**: 글 읽기 / 답글로 질문 / 확인하기 — 플랫폼마다 아래 「끝맺음」
- 쓰지 않는 것 (모든 플랫폼, 오류):
  - 낚시·과장: 「衝撃」「必見」「知らないと損」「ヤバい」「驚愕」「まだ〜してないの？」「〇〇な人は今すぐ」
  - 반응 구걸 (Meta·X가 노출을 줄인다): 「いいねして」「RTして」「リポストして」「シェアして」「フォローして」「保存して」「コメントして」
  - 겁주기 (common.md 4장): 「今すぐ対策しないと」「大変なことに」
  - 다른 회사·사람 계정 언급(@), 경쟁 회사 깎아내리기, 고객 이름·사례를 허락 없이
  - 「AIが書きました」류 메타 발언, 해시태그 나열로 문장 만들기
- 글 종류별 결
  - **보안 속보**: 「해당되는지 확인하는 법」 + 「할 일」이 중심. 사고 회사를 탓하지 않는다
  - **보안 대책**: 체크 항목 1개를 보여 주고 나머지는 글에서
  - **AI 사용법·업무 활용**: 편집부가 해 본 장면(무엇을 넣었더니 무엇이 나왔나)을 짧게. 프롬프트 전문은 쓰지 않는다 (글로 데려온다)
  - **AI 속보**: 「우리 업무에 무슨 뜻인가」 한 줄이 핵심. 기능 나열 금지
  - **AI 도입·개발 발주**: 비용·준비·판단 기준. 금액은 글에 있는 것만

#### X (훑어보는 실무자 — 「멈춰서 읽게」)
- 목소리: 편집부. 짧고 단정한 です・ます, 체언 끝맺음 가능. 「ヒカリです」 인사 없음, 「弊社」 없음
- 切り口: `数字` / `意外な事実` / `質問` 중 하나
- 틀: ① 훅 한 줄(수치·의외의 사실·질문) → ② 근거나 이유 한 줄 → ③ 할 일 또는 질문 한 줄 → 해시태그. 줄바꿈으로 덩어리 2~3개
- 답글: 「詳しくはこちら」만 쓰지 않는다 — 글에서 얻는 것을 한 줄로(「確かめる4項目と聞き方をまとめました」) + 링크
- 끝맺음: 질문 또는 할 일
- 예: `○○の期限は12月31日です。` / `「○○すれば安全」は半分だけ正解でした。` / `御社の○○、いま何番か分かりますか？`

#### Threads (가볍게 보는 개인 — 「이야기하듯」)
- 목소리: ヒカリちゃん. 혼잣말·대화체의 부드러운 です・ます. 「ヒカリです。」로 시작해도 된다. 「弊社」 없음, 번호 목록 없음
- 切り口: `試した` / `気づき` 중 하나 — 편집부가 해 보고 알게 된 것, 독자가 「나도?」 하고 생각할 것. 글에 실습이 없으면 `気づき`
- 틀: ① 알게 된 것 → ② 왜 놀랐나 / 무엇이 의외였나 → ③ 그래서 무엇을 보면 되나 → ④ **질문으로 끝낸다**(답글을 부른다) → 링크
- 문단은 1~2문장, 문단 사이 빈 줄. 표·기호 목록 쓰지 않는다
- 끝맺음: 독자가 답하기 쉬운 질문 (예/아니요나 한 단어로 답할 수 있는 것)
- 예: `古い設定のまま新しい版にしてみたら、安全な初期設定が効いていませんでした。`

#### Facebook (30~60대 사장·경영자 — 「옆에서 말을 건다」)
- 목소리: 정중한 です・ます. 「社長」「経営者の方」 같은 직함 부르기는 하지 않고 장면으로 부른다. 「弊社」 없음, 「ヒカリです」 없음
- 切り口: `場面` — 사장님이 실제로 겪을 장면 (거래처·제작 회사·직원·고객에게 들은 말, 청구서, 메일)
- 틀: ① 장면 한 줄(「○○から『△△』と言われたら」) → ② 결론 한 줄 → ③ 지금 할 일 1~2개(쉬운 말) → ④ 「記事にまとめました」
- 전문 용어는 쓰지 않거나 괄호로 풀이 (영문 기술 용어 그대로 금지 — PHP·AI·WordPress처럼 이미 익숙한 이름은 된다)
- 첫 줄 60자 이내 (모바일에서 접기 전에 보이게)
- 끝맺음: 「記事にまとめました」 + 할 일
- 예: `制作会社から「サーバーを新しくしましょう」と言われたら、まず聞いてほしいことがあります。`

#### LinkedIn (의사 결정하는 사람·거래처 — 「회사의 판단」)
- 목소리: 회사. 「弊社編集部では」로 판단 주체를 밝힌다(한 번). 단단한 です・ます. 가벼운 말투·이모지 없음. 「ヒカリです」 없음
- 切り口: `判断` — 비용·위험·일정·우선순위에 대한 회사의 판단
- 틀: ① **첫 두 줄에 판단 + 근거 수치** (「もっと見る」 전) → ② 번호 2~3개(사실 → 의미) → ③ 회사의 권고 한 줄 → 해시태그 2~3
- 대표 한마디(카드 `rep_comment`)가 있을 때만 첫머리에 「代表ヤンのひとこと」로 그대로 (철칙 1)
- 끝맺음: 권고 (「〜から確かめることをおすすめします」)
- 예: `○○への対応は、新機能より先に期限から決めるのが現実的です。`

#### note (차분히 읽는 사람 — 「읽을거리」, **블로그와 다른 검색어를 맡는다**, D76)
- **모든 글**을 올린다 (속보 포함, 하루 6편 — 사용자 결정 2026-11-21: note 안의 인기를 위해)
- note.com은 도메인이 강해 블로그 요약을 같은 키워드로 올리면 **블로그보다 위에 뜰 수 있다** → 블로그 요약이 아니라 각도를 바꾼 「편집부의 읽을거리」:
  - 속보: 切り口 `編集部メモ` — 「この知らせを見て編集部が最初に確かめたこと」
  - 깊이 있는 글: 切り口 `裏側`(やってみた裏側 — 실습이 있을 때) / `視点`(編集部の視点)
- 제목·첫 문단에 블로그 메인 키워드를 쓰지 않는다 (띄어쓰기만 다른 꼴 포함, 오류). 제목 첫 15자가 블로그 제목·og_title과 같으면 오류
- 목소리: ヒカリちゃん
- 틀: `### タイトル`(30자 안팎) → 인사 → 독자의 고민 → ■ 소제목 3~4개(각 3~5문장 — 편집부가 확인한 순서·생각) → 「ブログでは〜までまとめています」 → `全文はブログで` + 링크 → 해시태그
- 블로그 본문 문장을 옮기지 않는다 (30자 이상 같으면 오류). 표·체크리스트 전체는 블로그에만

### 고객 창구 (D75)
- 댓글·답글·DM은 **사람이** 본다 — 하루 1번 이상. 에이전트는 답하지 않는다 (Windsor 댓글·메시지 기능을 부르지 않는다)
- 문의·상담 같은 댓글은 공개 답글에서 길게 답하지 않고, 상담 창구로 안내한다: `ご質問ありがとうございます。詳しくはこちらからお気軽にご相談ください（無料）→ <상담 링크>`
- 비판·잘못 지적은 하루 안에 사실을 확인하고, 글이 틀렸으면 정정 방침대로 고친 뒤 답한다
- SNS 프로필(소개·링크)은 블로그와 상담 페이지로 이어지게 둔다 — 사람이 1회 설정 (남은 일)
- 게시 뒤 반응(노출·클릭·댓글)은 blog-measure에서 플랫폼별로 본다 → 切り口·틀을 고친다
